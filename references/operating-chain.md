# Operating Chain

Translate the role into an operating map:

```text
Business objective
→ target user/customer
→ opportunity or list creation
→ qualification and priority
→ execution
→ cross-team coordination
→ conversion or delivery
→ data capture
→ review and optimization
→ compliance and risk
```

## Step record

For every step capture:

| Field | Required answer |
| --- | --- |
| Step ID | stable identifier such as `OPS-03` |
| Purpose | why the step exists |
| Owner | role or team accountable |
| Inputs | data, asset, inventory, brief, lead, or approval |
| Actions | concrete work, not skill adjectives |
| Output/artifact | shortlist, brief, email, CRM record, post, report |
| Tool category | capability category; name a product only when verified/relevant |
| Metric | leading, quality, and outcome signals |
| Handoff | recipient and acceptance condition |
| Failure mode | common breakdown and diagnosis |
| Regional difference | local norm that changes the step |
| Interview probe | likely skeptical question |

## Quality rules

- Link every JD requirement to at least one step or mark it decorative/unclear.
- Separate activity metrics from business outcomes.
- Show who owns conversion when the role owns only the upstream signal.
- Record artifacts because artifacts become evidence and work-sample candidates.
- Do not name a tool merely to sound current; tool knowledge is useful only in a real task.
- Surface bottlenecks created outside the role instead of pretending individual effort solves them.

## Operating-map output

Use [templates/role-operating-map.md](../templates/role-operating-map.md). End with the three most probable operating bottlenecks, evidence for each, and the interview question that could reverse the diagnosis.
